## 0. Как читать этот документ

**Что проверено.** Аудит сделан по исходному коду, а не по скриншотам. Ссылки вида `src/components/Shell.jsx` указывают, где живёт проблема. Цифры контраста посчитаны по формуле WCAG из значений токенов в `src/styles.css`.

**Что известно о стеке (факты из репозитория):**

| Слой | Факт |
|---|---|
| Фронтенд | React 19.3, React Router 7, Vite 8, `lucide-react`, KaTeX; ленивые страницы через `React.lazy` в `src/App.jsx` |
| Бэкенд | PHP-скрипты в `public/api/` на хостинге reg.ru; базы данных нет, данные в JSON-файлах |
| Данные о помещениях | Статический массив `rooms` в `src/data.js` (47 помещений, 2 этажа, координаты на плане) |
| Планы | `map1lower.svg`, `map2lower.svg` + слой стен/дверей из `src/map-art.js` |
| Маршрутизация | Клиентская, `src/map-routing.js`: коридорный граф, лифт и три лестницы |
| Расписание | **Только звонки** (`src/bells.js`). Личного расписания, групп, дисциплин и аудиторий занятий в данных нет |
| Преподаватели | `public/teachers.json`: ФИО, должность, предметы. Кабинет преподавателя выводится по предмету, а не хранится |
| ИИ | `public/api/ai-chat.php` → DeepSeek, база знаний `ai-knowledge.txt`, ответ — Markdown; ссылки `/map…` и `/route…` клиент превращает в кнопки (`src/ai-chat.js`) |
| Корпуса | В данных **один корпус**, два этажа |
| Темы | Светлая, тёмная, «Пикми»; язык RU/EN |

**Технические допущения**, которые нужно подтвердить до старта (помечены в тексте как `[ДОПУЩЕНИЕ]`):

- Д-1. Появится источник расписания групп (выгрузка из учебной части в JSON/CSV по расписанию cron или ручная загрузка через `/admin`). Без него пункты 04 и 06 (сценарии A и C) реализуются только в урезанном виде, описанном ниже.
- Д-2. Данных о занятости аудиторий в реальном времени нет и в ближайшей версии не будет. «Занята/свободна» выводится только из расписания (Д-1), с явной пометкой «по расписанию».
- Д-3. Второй корпус возможен в будущем. Архитектура карты должна поддерживать N корпусов, но UI переключателя корпусов скрыт, пока корпус один.
- Д-4. Хостинг остаётся статическим + PHP. Service Worker разрешён (HTTPS есть).

**Зависимости от бэкенда** помечены как `[BACKEND]` и оцениваются отдельно от фронтенда.

## Раздел 1. Общий UX/UI-аудит

### 1.1. Главные проблемы интерфейса

| # | Проблема | Где | Почему это важно |
|---|---|---|---|
| A-1 | **Четыре независимые реализации поиска** с разной логикой: `HomeSearch` (4 места + 2 преподавателя), `SearchDialog` в шапке (7 + 3, есть «Недавние», «Рядом»), `RoomSearchSelect` на карте и маршруте, поиск в меню, который открывает тот же диалог | `src/pages/HomePage.jsx`, `src/components/Shell.jsx`, `src/components/RoomSearchSelect.jsx` | Один и тот же запрос даёт разный набор и порядок результатов на разных экранах. Это ломает предсказуемость и удваивает стоимость поддержки |
| A-2 | **Карта не видна на первом экране главной.** Первый экран: заголовок, абзац, поиск, две CTA, 3D-сцена; ниже `GuideBoard`, «Мой день», «Часто ищут». Карта только по ссылке | `HomePage.jsx` | Основная ценность продукта (карта и маршрут) отделена от пользователя минимум одним переходом |
| A-3 | **«Мой день» не персональный.** Показывает звонки для всех; нет аудитории, дисциплины, преподавателя, кнопки маршрута к паре | `src/components/HomeDashboard.jsx`, `src/bells.js` | Виджет занимает место, но не отвечает на главный вопрос студента «куда мне идти сейчас» |
| A-4 | **Нет нижней навигации на телефоне.** Шапка + бургер с 14 пунктами в 3 группах + язык, тема, размер текста, обучение | `Shell.jsx` | Основные действия вне зоны большого пальца; навигация требует 2 нажатий |
| A-5 | **CSS-слой из ~50 файлов, подключённых глобально**, где поздние файлы переопределяют ранние (`refinement`, `polish`, `premium`, `finish`, `clean`, `soft`, `visual-pass`, `align` …), 100+ `!important`, 49 разных значений `max-width` в медиазапросах | `src/main.jsx`, `src/*.css` | Любое изменение UI непредсказуемо, регрессии в трёх темах. Основная причина «визуального шума» — отсутствие единой системы токенов |
| A-6 | **Контраст ниже WCAG AA** у служебных цветов: `--muted #697891` на фоне `--bg #f4f7fc` = 4,16:1 (нужно 4,5); `--muted-2 #8d9ab0` на белом = 2,84:1; кольцо фокуса `#6e96ff` на белом = 2,81:1 (нужно 3:1 по 1.4.11/2.4.13) | `src/styles.css` | Нарушение AA; плохо читается на улице с телефона |
| A-7 | **ИИ — универсальный чат**, а не инструмент навигации: квизы, графики, формулы, фото. Нет структурированного ответа «место → этаж → кнопки». Данных о расписании групп у модели нет, поэтому сценарии A и C либо отказ, либо риск выдумки | `src/pages/AiAgentPage.jsx`, `public/api/ai-chat.php` | Ответ о местоположении опирается на текст модели, а не на `data.js`; кнопки появляются только если модель сама вставила правильную ссылку |
| A-8 | **Нарушения ARIA в подсказках поиска**: внутри `role="option"` лежат ссылки и кнопка «Маршрут» (вложенные интерактивные элементы); `aria-live="polite"` висит на всём списке результатов, и скринридер зачитывает список при каждом символе; в `SearchDialog` `aria-expanded="true"` всегда | `Shell.jsx` | Скринридер-пользователь не может предсказуемо выбрать результат |

| A-10 | **Второстепенное в первичной навигации**: в шапке «Преподаватели» и «ИИ-помощник (АЛЬФА)» на одном уровне с «Картой» и «Маршрутом»; переключатель темы — отдельная кнопка в шапке | `src/data.js` → `navigation` | Шум и размывание иерархии |

### 1.2. Ключевые точки улучшения

1. **Единый поисковый движок + единый UI-компонент подсказок** (A-1, A-8). Даёт предсказуемость на всех экранах.
2. **Главная = поиск + «Мой день» + карта** на первом экране (A-2, A-3).
3. **Карта как основной экран на телефоне**, нижняя навигация, полноэкранный режим и нижняя шторка с карточкой места (A-4).
4. **Design tokens и чистка каскада CSS** (A-5, A-6). Без этого остальные пункты будут добавлять ещё слои.
5. **ИИ отвечает структурированно**: сервер возвращает не только текст, но и `actions` (открыть место, построить маршрут), а факты о местах берутся из `data.js`, а не из модели (A-7).

### 1.3. Приоритеты продукта

Порядок важности сценариев (из него следуют все решения в документе):

1. **Найти место и дойти до него** — поиск → карта → маршрут. Цель: ≤ 3 действия от открытия сайта до маршрута на экране.
2. **Понять, куда идти на ближайшую пару** — «Мой день». Цель: 1 нажатие до маршрута. `[ДОПУЩЕНИЕ Д-1]`
3. **Получить ответ на вопрос о колледже** — ИИ.
4. Всё остальное (игры, экскурсия, таблички, документация) — вторичные разделы, без мест в первичной навигации.

### 1.4. Ожидаемый результат и как его измерять

Цель «100/100» не выставляется оценкой; ниже объективные критерии, при выполнении которых направление считается доведённым до целевого уровня.

| Направление | Критерий достижения целевого уровня | Как измерить |
|---|---|---|
| UX | Медианное число действий «открыл сайт → маршрут к кабинету по номеру» ≤ 3 (ввод, выбор подсказки, «Маршрут»). Успешность задачи на 5 тестовых пользователях ≥ 90 %, без подсказок модератора | Юзабилити-тест по сценариям раздела 8; события `stats.php` |
| UI | 0 значений цвета, отступа, радиуса, тени, размера шрифта вне токенов в новых/изменённых компонентах; ≤ 5 размеров шрифта и ≤ 3 начертаний в интерфейсе | Stylelint-правило на hex/px вне `tokens.css` |
| Адаптивность | Нет горизонтальной прокрутки на ширинах 320, 360, 375, 390, 414, 768, 1024, 1280, 1440; все цели ≥ 44×44 CSS px на `pointer: coarse` | Playwright-скрипт с проверкой `scrollWidth <= clientWidth` и замером целей |
| Доступность | 0 нарушений axe-core уровня serious/critical на 8 ключевых страницах; все сценарии раздела 8 проходятся только клавиатурой и с VoiceOver/TalkBack | axe в Playwright; ручной прогон |
| Производительность | Lighthouse Mobile (Moto G Power, Slow 4G) ≥ 95 по 4 категориям на `/`, `/map`, `/route`; LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на 75-м процентиле полевых данных | Lighthouse CI; `web-vitals` → `stats.php` |
| Реализуемость | Каждая задача P0–P1 имеет оценку и не требует смены хостинга | Матрица раздела 6 |

### 01. Глобальная навигация и Header

**Текущая проблема.**
- Desktop: логотип, 5 пунктов навигации с иконками и бейджем «АЛЬФА», кнопка поиска с `K`, кнопка темы, колокольчик, бургер. 9–10 интерактивных элементов в 64 px.
- Mobile: логотип, колокольчик, «Карта», бургер; меню на весь экран с 14 карточками, сегментами языка/темы/текста и кнопкой обучения.
- Дублирование: поиск в шапке, в hero главной и в меню; «Карта» дважды (пункт навигации и `mobile-map-link`).
- Поведения шапки при прокрутке не задано явно; шапка липкая, занимает высоту на карте.

**Цель.** Шапка решает две задачи: перейти в основной раздел и начать поиск. Всё остальное — в меню «Ещё».

**Предлагаемое решение. Итоговая структура Header (Desktop ≥ 1024 px), слева направо:**

| Порядок | Элемент | Назначение |
|---|---|---|
| 1 | Логотип «ЛОГОС» (знак + слово, без подписи «ПУТЕВОДИТЕЛЬ» при ширине < 1280) | Переход на главную |
| 2 | Навигация: **Карта · Маршрут · Расписание · Помощник** | 4 основных раздела. «Кабинеты» и «Преподаватели» уходят внутрь поиска и в меню «Ещё»: их задачу полностью закрывает поиск |
| 3 | Поле-кнопка поиска «Кабинет, место или преподаватель» с подсказкой `/` и `Ctrl K` | Открывает единый поиск (см. 05). Растягивается, занимает свободное место, min 240 px, max 420 px |
| 4 | Колокольчик уведомлений | Только если пользователь подписан на push или есть непрочитанные объявления. Иначе скрыт |
| 5 | Кнопка «Ещё» (иконка `Menu`, подпись «Ещё» видна при ≥ 1280) | Поповер: Кабинеты, Преподаватели, Пространства, Первая неделя, Игры, Экскурсия, Таблички, О проекте, Сообщить о проблеме; блок настроек: язык, тема, размер текста, обучение |

Убирается: отдельная кнопка темы в шапке (переезжает в «Ещё»), бейдж «АЛЬФА» в навигации (переезжает на страницу помощника, под заголовок), иконки у пунктов текстовой навигации на desktop (текст однозначен, иконки добавляют шум).

> «Расписание» — новый раздел, `[ДОПУЩЕНИЕ Д-1]`. Пока данных нет, пункт ведёт на страницу звонков и подписки на напоминания (сейчас это `/notifications`), подпись «Звонки».

**Визуальная спецификация.**
- Высота: 64 px (desktop), 56 px (mobile). Фон `--c-surface`, нижняя граница 1 px `--c-border`. Без тени в покое.
- Пункт навигации: текст `--text-sm` / 500, padding `0 --space-3`, высота 40 px, радиус `--radius-sm`.
- Активный пункт: цвет `--c-primary`, фон `--c-primary-subtle`, `aria-current="page"` (NavLink ставит его сам). Не подчёркивание и не только цвет: фон даёт второй признак.
- Hover (только `@media (hover: hover)`): фон `--c-surface-hover`.
- Поле поиска: высота 40 px, фон `--c-surface-sunken`, граница 1 px `--c-border`, иконка `Search` 16 px слева, `kbd` справа.

**Логика работы.**
- Прокрутка вниз > 64 px на страницах с документной прокруткой (главная, справочники): шапка остаётся видимой (sticky), получает тень `--shadow-1`. **Не прятать шапку при прокрутке**: скрывающиеся шапки дают сдвиги и «прыжки» под пальцем, а поиск должен быть всегда доступен.
- На `/map` и `/route` (desktop) шапка статична, карта занимает `100dvh - 64px` и прокручивается внутри себя; документ не прокручивается.
- Горячие клавиши: `/` и `Ctrl/Cmd+K` открывают поиск, если фокус не в поле ввода. Сейчас используется `K` (а также `к`/`л`) без модификатора (`src/shortcuts.js`): вне полей ввода он срабатывает от одного нажатия, это конфликт с WCAG 2.1.4 (односимвольные сочетания). Оставить `/` (общепринятый) только при отсутствии фокуса в поле и `Ctrl/Cmd+K`; добавить в «Ещё» → «Настройки» переключатель «Горячие клавиши» (2.1.4 допускает односимвольное сочетание, если его можно выключить).
- «Ещё»: поповер на desktop (ширина 360 px, выравнивание по правому краю кнопки), закрывается по Esc, клику вне, выбору пункта; фокус возвращается на кнопку.

**Состояния.** default, hover, active (нажатие: фон `--c-surface-pressed`), focus-visible (кольцо, раздел 5), current (активный раздел), menu-open (`aria-expanded="true"`).

**Компактное состояние.**
- 768–1023 px: логотип-знак без слова; 4 пункта навигации текстом; поиск сворачивается в иконку-кнопку 40×40 с `aria-label="Найти"`; «Ещё».
- < 768 px: см. 07 — шапка 56 px: логотип-знак, поле-кнопка поиска на всю оставшуюся ширину, колокольчик (условно). Разделы — в нижней навигации. Бургер убирается.

**Технические требования.**
- `Header` разбить на `HeaderBar`, `PrimaryNav`, `SearchTrigger`, `MoreMenu`. Меню-конфигурация — один массив в `src/navigation.js`, используемый шапкой, нижней навигацией, меню «Ещё» и футером (сейчас `navigation` в `data.js` и `menuGroups` в `Shell.jsx` — два источника).
- `MoreMenu` на desktop — `<button aria-expanded aria-controls>` + `<div>` с обычными ссылками (не `role="menu"`: это навигация, а не меню приложения).
- Без изменения поведения View Transitions для темы, но запуск только из «Ещё».

**Критерии приёмки.**
1. На 1280 px в шапке ровно: логотип, 4 пункта, поиск, (колокольчик), «Ещё». Нет кнопки темы.
2. Активный раздел имеет `aria-current="page"` и отличается не только цветом (фон).
3. `K` при фокусе вне полей не открывает поиск; `/` и `Ctrl+K` открывают; при выключенных горячих клавишах `/` не работает, `Ctrl+K` работает.
4. Нет ни одного пункта, который встречается в шапке дважды.
5. При прокрутке главной шапка не меняет высоту, CLS от шапки = 0.
6. Esc в «Ещё» закрывает поповер и возвращает фокус на кнопку.

**Приоритет:** P1 (структура), P0 (горячая клавиша `K` — нарушение 2.1.4).

### 02. Интерактивная карта и навигация по корпусу

**Текущая проблема.**
- Панорамирование сделано прокруткой контейнера (`scrollLeft/scrollTop`), масштаб — собственным pinch-обработчиком и `zoomFrame` (`src/components/FloorMap.jsx`, `src/map-zoom.js`). Колесо мыши не масштабирует, на Safari нужны обходы (комментарии в коде). Есть 3D-режим (`rotateX(46deg)`), который ухудшает читаемость номеров.
- Подписи: два режима «показывать/скрывать подписи» вручную в настройках карты, а не по масштабу. На мобильном при 100 % номера кабинетов мелкие.
- Высокий контраст — отдельный переключатель (`map-contrast.js`), т. е. базовый режим контраст не обеспечивает.
- Нет легенды; лестницы/лифт различаются только подписью.
- Переход на этаж выбранного кабинета есть (`?floor=&room=`), но анимации/подсказки «Вы перешли на 2 этаж» нет.

**Цель.** Карта читаема без переключателей; выбранное место и маршрут находятся глазом за < 1 с; управление одинаково мышью, пальцем и клавиатурой.

**Предлагаемое решение.**

*Визуальная иерархия объектов (сверху вниз по значимости, порядок отрисовки обратный):*

| Слой (z) | Объект | Стиль (светлая тема) |
|---|---|---|
| 1 | Фон этажа, вне здания | `--c-map-bg` |
| 2 | Коридоры | `--c-map-corridor` (светлее помещений), без обводки |
| 3 | Помещения обычные | Заливка `--c-map-room`, обводка 1 px `--c-map-wall` |
| 4 | Помещения по категории | Тонкая цветная полоса 4 px по верхней грани или маленький значок категории, **не** полная заливка цветом: заливка резервируется под состояния |
| 5 | Стены и двери | Стены 2 px `--c-map-wall`; дверь — разрыв стены + засечка 2 px `--c-map-door` |
| 6 | Вертикальные связи | Лестница: значок `Footprints`/ступени 20 px; лифт: значок `ArrowUpDown` в квадрате; фон `--c-map-vertical` |
| 7 | Состояния мест | См. таблицу состояний ниже |
| 8 | Маршрут | Линия 6 px `--c-route` + подложка 10 px `--c-map-bg` (белая «окантовка» для контраста на любом фоне) |
| 9 | Точки A и B, «Вы здесь» | Маркеры, см. ниже |
| 10 | Подписи | Номер кабинета + короткое название |

*Состояния помещения:*

| Состояние | Заливка | Обводка | Подпись | Когда |
|---|---|---|---|---|
| Обычное | `--c-map-room` | 1 px `--c-map-wall` | `--c-map-label` | По умолчанию |
| Hover (мышь) | `--c-map-room-hover` | 1 px `--c-primary` | без изменений | `pointer: fine` |
| Фокус клавиатуры | как hover | кольцо 3 px `--c-focus` снаружи контура | без изменений | `:focus-visible` |
| Выбрано | `--c-primary-subtle` | 3 px `--c-primary` | `--c-primary-strong`, 600 | Выбор из поиска/клика |
| Пункт назначения маршрута | как «Выбрано» + маркер B | | | Есть маршрут |
| Занято по расписанию `[Д-1, Д-2]` | без изменения заливки + точка-индикатор 8 px `--c-warning` у номера | | «Идёт занятие до 12:10» в карточке | Расписание показывает пару |
| Недоступно | штриховка 45° `--c-map-disabled` | пунктир 1 px | `--c-text-subtle` | Закрыто объявлением (`notices.json`) или служебное |
| Отфильтровано (не входит в фильтр) | opacity .35 | | скрыта | Фильтр категорий |

Принцип: состояние кодируется минимум двумя признаками (цвет + толщина обводки/штриховка/значок), чтобы работало при нарушениях цветовосприятия (WCAG 1.4.1).

*Маркеры маршрута:*
- Начало (A): круг 16 px, заливка `--c-surface`, обводка 4 px `--c-route`, подпись «Старт» в чипе.
- Конец (B): каплевидный пин 28 px `--c-route`, внутри иконка флажка; на плане подсвечена дверь помещения (засечка 4 px).
- «Вы здесь»: синий круг 14 px + полупрозрачный круг точности (радиус = точность GPS/BLE в масштабе плана) + сектор направления по компасу, если есть.
- Переход между этажами на маршруте: в точке лестницы/лифта маркер-чип «↑ на 2 этаж» (кнопка, переключает этаж).

**Логика масштабирования и перемещения.**
- Перейти с прокрутки контейнера на **трансформацию одного `<g>` внутри SVG** (`transform: matrix(...)`) с собственными pan/zoom на Pointer Events. Причина: прокрутка контейнера конфликтует с прокруткой страницы и pinch Safari, не даёт масштабировать вокруг точки под пальцем/курсором и требует обходов, уже накопленных в `FloorMap.jsx`.
- Диапазон масштаба: `minZoom` = «весь этаж вписан в окно» (fit), `maxZoom` = 4 × fit. Шаг кнопок ±: ×1,5. Колесо: `ctrlKey`-колесо и трекпад-pinch масштабируют вокруг курсора; обычное колесо **панорамирует** только в полноэкранном режиме, во встроенной карте на главной — прокручивает страницу (см. 07, конфликт жестов).
- Двойной тап/клик по пустому месту: zoom ×2 вокруг точки. Двойной тап по помещению: выбор + zoom к нему.
- Границы: план нельзя утащить так, чтобы в окне осталось < 25 % плана (мягкий упор с возвратом 200 мс).
- Инерция панорамирования: да, на `pointer: coarse`, затухание 300–400 мс; отключается при `prefers-reduced-motion`.
- Кнопки управления (правый нижний угол карты, колонка): «+», «−», «Вписать этаж», «Моё местоположение». Каждая 44×44.
- Клавиатура при фокусе на карте (`<div role="application">` не используется; карта — `tabindex="0"` контейнер с `aria-describedby` на подсказку): стрелки — панорамирование на 10 % окна, `+`/`-` — масштаб, `0` — вписать, `Tab` — переход по помещениям в порядке номеров (только видимые в окне и выбранные), `Enter` — выбрать, `Esc` — снять выбор.
- Сохранение вида: при смене этажа масштаб и центр сбрасываются к «вписать», кроме случая, когда этаж сменился из-за маршрута — тогда центр на точке перехода (лестнице/лифте).

**Поведение подписей при zoom (LOD — уровень детализации).** Пороги — в единицах «эффективный размер шрифта на экране», а не в процентах масштаба, чтобы одинаково работать на телефоне и мониторе:

| Уровень | Условие | Что показывается |
|---|---|---|
| L0 | Помещение на экране < 28 px по меньшей стороне | Только значки вертикальных связей и выбранное помещение |
| L1 | 28–60 px | Номер кабинета (или короткое имя для общих пространств: «Столовая», «WC») |
| L2 | > 60 px | Номер + название в 1–2 строки (`map.lines` из `data.js`) |

- Размер шрифта подписи на экране держится в пределах 11–16 px: SVG-текст получает `font-size = базовый / zoom` с ограничением (подпись не растёт бесконечно при zoom-in и не становится 4 px при zoom-out).
- Если подпись не помещается в прямоугольник помещения на текущем уровне — она скрывается (проверка по предвычисленной ширине, `getComputedTextLength` один раз при загрузке, кешируется).
- Выбранное помещение и точки маршрута подписаны всегда, на любом уровне.
- Переключатель «Показывать подписи» из настроек карты убирается (LOD делает его ненужным). Переключатель высокого контраста **остаётся** как пользовательская настройка, но базовая палитра уже должна проходить 3:1 для границ и 4,5:1 для подписей.

**Переключение корпусов и этажей.**
- Переключатель этажей: вертикальная сегментированная группа у левого края карты (desktop) / над нижней шторкой (mobile): кнопки «2», «1» (сверху вниз, как в здании). Каждая 44×44, активная — `--c-primary` фон, `aria-pressed="true"`. Если на этаже есть точка маршрута, на кнопке — точка-индикатор `--c-route`.
- Корпуса `[ДОПУЩЕНИЕ Д-3]`: при количестве корпусов > 1 над этажами появляется селект корпуса. Модель данных: `buildings[] → floors[] → rooms[]`; сейчас `building` по умолчанию `'main'`, поле добавить в `room()` без изменения UI.
- Автопереход на этаж выбранного места: при выборе места на другом этаже — смена этажа (анимация 02/08), затем центрирование и zoom к месту так, чтобы место занимало ~30 % меньшей стороны окна, но не больше `maxZoom`. Тост не нужен: смена индикатора этажа + объявление в `aria-live` «Второй этаж, кабинет 217».

**Отображение переходов между этажами в маршруте.**
- Маршрут разбит на сегменты по этажам. На текущем этаже показан только его сегмент; сегмент другого этажа не рисуется полупрозрачно (это путает).
- В точке перехода — чип-кнопка «Подняться на 2 этаж по лифту →». Нажатие: смена этажа, маршрут продолжается от той же лестницы/лифта.
- Список шагов маршрута (уже есть `src/route-steps.js`) содержит шаг «Поднимитесь на лифте на 2 этаж».

**Легенда.**
- Кнопка «Легенда» (иконка `Info`, 44×44) в колонке управления; открывает поповер (desktop) / шторку (mobile) с 6 строками: коридор, помещение, выбрано, недоступно, лестница, лифт, маршрут, «Вы здесь». Образцы — те же SVG-символы, что на карте (`<use href="#sym-stairs">`), не картинки.
- Легенда не открыта по умолчанию; при первом визите на карту — одноразовая подсказка-коучмарк «Значки на карте» (хранится в `localStorage`, ключ вписать в `privacy-items.js`).

**Обработка отсутствующего маршрута.**

| Причина | Сообщение | Действие |
|---|---|---|
| Начало и конец совпадают | «Вы уже на месте: это одно и то же помещение» | — |
| Лестница/лифт закрыты объявлением, другие варианты есть | Маршрут строится по доступному варианту; плашка «Лифт сегодня не работает — маршрут по центральной лестнице» | «Подробнее» → объявление |
| Все варианты перехода закрыты | «Сейчас нельзя пройти на 2 этаж: закрыты лифт и лестницы. Обратитесь на пост охраны у главного входа» | Кнопка «Показать вход» |
| Пользователь выбрал «без лестниц», а лифт закрыт | «Маршрут без лестниц сейчас недоступен» | «Показать маршрут по лестнице» |
| У помещения нет двери/координат в данных | «Для этого места ещё нет точки входа на плане» | «Сообщить о проблеме» (есть `ReportProblem`) |
| Ошибка вычисления (исключение) | «Не получилось построить маршрут» | «Попробовать снова», логирование в `client-error.php` |

**Поведение при отсутствии данных.**
- План этажа не загрузился (SVG): скелетон контура этажа 1:1 по размеру, через 8 с — ошибка «План этажа не загрузился» + «Повторить». Список мест (альтернативное представление, 09) показывается всё равно — он из `data.js`, сеть не нужна.
- На этаже нет мест по фильтру: пустое состояние в списке «На этом этаже нет мест из категории “Лаборатории”» + «Показать все места».
- `?room=` указывает на несуществующий id: карта открывается на этаже 1, плашка «Место не найдено. Возможно, оно переехало» + поиск с фокусом.

**Технические требования.**
- Компонент `FloorMap` разделить: `MapViewport` (pan/zoom, жесты, клавиатура), `FloorLayer` (статичная геометрия этажа, мемоизирована, перерисовывается только при смене этажа/темы), `StateLayer` (выбор, фильтр, недоступность), `RouteLayer`, `MarkerLayer`, `LabelLayer` (LOD).
- Pan/zoom: состояние в `useRef`, применение через `requestAnimationFrame` и запись `transform` атрибута напрямую в `<g>`; React-стейт обновляется только по окончании жеста (для LOD — с троттлингом 100 мс). Ни одного `setState` на `pointermove`.
- Контейнер карты: `touch-action: none` только в полноэкранном режиме или после первого тапа по карте (см. 07); иначе `touch-action: pan-y` (вертикальная прокрутка страницы работает, горизонтальный pan и pinch — у карты).
- 3D-режим (`mode3d`) переводится в «экспериментальное» в настройках карты и по умолчанию выключен; в 3D не показывать номера мельче 12 px.
- Геометрия этажа — один инлайновый SVG на этаж, оптимизированный SVGO (см. 10), символы через `<symbol>`/`<use>`.
- Hit-testing: клики обрабатываются одним делегированным слушателем на `<g>` помещений (`data-room-id`), не по слушателю на каждое помещение.

**Адаптивное поведение.**
- Desktop: карта слева (гибкая ширина), справа панель 360 px: поиск, карточка места, маршрут. Этажи — колонка слева на карте.
- Tablet: панель 320 px справа в альбомной; в портретной — нижняя шторка как на mobile.
- Mobile: см. 07.

**Критерии приёмки.**
1. На 375 px при масштабе «вписать этаж» каждый номер учебного кабинета либо виден с экранным размером ≥ 11 px, либо скрыт целиком (нет обрезанных/наложенных подписей). Проверка: скриншоты этажей 1 и 2.
2. Контраст: граница помещения к фону ≥ 3:1; подпись к заливке ≥ 4,5:1; маршрут к коридору и к помещению ≥ 3:1 — во всех 3 темах и в режиме высокого контраста.
3. Pinch, ctrl+колесо, двойной тап масштабируют вокруг точки жеста: точка под пальцем/курсором смещается не более чем на 4 px.
4. Во время pan/zoom на Moto G Power-классе (CPU throttling ×4 в DevTools) нет длинных задач > 50 мс; FPS ≥ 50 по Performance-панели.
5. Выбор места на другом этаже: этаж переключается, место в центре окна, объявление для скринридера звучит один раз.
6. Маршрут с переходом: на этаже 1 видна только часть до лестницы и чип «на 2 этаж»; нажатие чипа показывает продолжение.
7. Все 6 сценариев таблицы «отсутствующий маршрут» воспроизводятся и показывают указанный текст (тест на `map-routing.js` + e2e).
8. Карта полностью управляется клавиатурой по описанной схеме.

**Приоритет:** P0 — контраст, LOD подписей, маршрут/маркеры, автопереход на этаж, ошибки маршрута; P1 — новый pan/zoom, легенда; P2 — модель корпусов; P3 — 3D-режим.

### 03. Первый экран (Hero-блок)

**Текущая проблема.** Hero содержит H1 «Где найти кабинет», абзац-инструкцию, подпись к полю, поле, две CTA («Смотреть карту», «Построить маршрут»), 3D-сцену с подписью-примером маршрута (desktop с мышью). Ниже `GuideBoard` (для новичков), «Мой день», «Часто ищут». Карты на главной нет. 3D-сцена — самый тяжёлый элемент первого экрана, но не несёт данных пользователя.

**Цель.** За первый взгляд пользователь видит: где искать, что у него сейчас по расписанию, план здания.

**Предлагаемое решение. Композиция Desktop (1280×800, видимая область ≈ 736 px под шапкой):**

```
┌────────────────────────────────────────────────────────────────────┐
│ Header 64                                                          │
├────────────────────────────────────────────────────────────────────┤
│ Hero ≈ 200 px (27 % высоты окна)                                   │
│  H1 «Найдите кабинет и постройте маршрут» (--text-2xl)             │
│  [ Поиск: номер кабинета, место или преподаватель   🎤  → ]  640px │
│  Чипы: Столовая · Библиотека · Учебная часть · Туалет · Медпункт   │
├───────────────────────────────┬────────────────────────────────────┤
│ Карта-превью (этаж 1)  ~60 %  │ «Мой день» ~40 %                   │
│ высота 440, кнопки этажей,    │ карточка пары (04)                 │
│ «Открыть карту ↗»             │ «Мои места», недавние маршруты     │
└───────────────────────────────┴────────────────────────────────────┘
↓ ниже: «Где ближайший», для новичков — GuideBoard
```

**Композиция Mobile (390×844, видимая ≈ 790 под шапкой 56 и над нижней навигацией 64 + safe area):**

```
Header 56: логотип-знак · [Поиск…] · (🔔)
Hero ≈ 120 px: H1 одной строкой (--text-xl) + чипы быстрого поиска (горизонтальная прокрутка)
«Мой день»: компактная карточка пары 132 px (04)
Карта-превью: 240 px, без жестов (тап → полноэкранная карта)
Bottom nav 64
```

- Поиск в mobile-hero не дублируется: поле в шапке и есть поиск. В hero только H1 и чипы. Это исключает «два поля поиска на одном экране».
- Desktop: поле поиска в hero — главный вход; кнопка поиска в шапке на главной **скрыта**, пока hero-поле в зоне видимости (`IntersectionObserver`), и появляется, когда hero уходит из окна. Так поиск не дублируется визуально.
- Абзац-инструкция удаляется: плейсхолдер и подсказки поиска объясняют то же самое.
- CTA «Смотреть карту» заменяется самой картой-превью; CTA «Построить маршрут» — пункт нижней навигации/шапки.
- 3D-сцена `HeroScene` убирается с главной (переносится на `/tour`, где она по смыслу). Визуальная идентичность сохраняется: фирменный цвет `--c-primary` в фоне hero (плоский градиент от `--c-primary-subtle` к `--c-bg`, без анимации), логотип, шрифт Onest.

**Визуальная спецификация.** H1: Onest 700, desktop 32/40, mobile 24/30. Поле hero: высота 56 px, радиус `--radius-lg`, тень `--shadow-1`, шрифт 18 px (чтобы iOS не зумил: ≥ 16 px). Чипы: высота 36 (визуально) с областью нажатия 44 (padding-block), `--radius-full`, фон `--c-surface`, граница `--c-border`.

**Логика работы.**
- Чипы — это готовые запросы: нажатие открывает место на карте-превью (desktop: карта-превью центрируется и подсвечивает место; кнопка «Маршрут» появляется в мини-карточке над картой) или открывает `/map?room=` (mobile).
- Карта-превью — тот же `FloorMap` в режиме `preview`: без жестов pan/zoom (кроме кнопок этажа), клик по помещению выбирает его и показывает мини-карточку «Кабинет 217 · 2 этаж · [Маршрут] [Открыть на карте]». Загружается лениво, когда блок ближе 200 px к окну (на desktop он в первом экране — значит сразу, но после LCP).
- Для «новичков» (нет избранного и недавних) под «Мой день» показывается `GuideBoard`, как сейчас; для остальных — ниже на странице.

**Состояния.** Hero не имеет собственных состояний, кроме поиска (05). Карта-превью: skeleton (контур этажа), ready, error («План не загрузился · Повторить»).

**Технические требования.**
- LCP-элемент — H1 (текст), не картинка и не canvas. Шрифт Onest с `font-display: swap` и `preload` для начертания 600/700 кириллицы (subset `cyrillic`).
- Удалить импорт `@fontsource-variable/caveat` из глобального бандла (`main.jsx`); подключать только в теме «Пикми».
- Высота hero фиксирована CSS (`min-height` нет, явная высота контента), чтобы «Мой день» и карта не прыгали при загрузке (CLS).

**Адаптивное поведение.** ≥ 1024: две колонки (карта 3fr / «Мой день» 2fr). 768–1023: «Мой день» над картой на всю ширину, карта 360 px. < 768: как в схеме mobile.

**Критерии приёмки.**
1. Desktop 1280×800: hero ≤ 40 % высоты окна (≤ 320 px), поле поиска, карточка «Мой день» и ≥ 50 % карты-превью видны без прокрутки.
2. Mobile 390×844: H1, чипы, карточка пары и верх карты-превью видны без прокрутки; на экране ровно одно поле поиска.
3. На главной нет WebGL/3D-кода в начальной загрузке (проверка: в Network нет чанка `HeroScene`).
4. LCP на главной (Lighthouse Mobile) ≤ 2,0 с, CLS ≤ 0,05.
5. Чип «Столовая» → место выделено на превью/открыто на карте за 1 нажатие.

**Приоритет:** P0.

### 04. Персональный виджет «Мой день»

**Текущая проблема.** `HomeDashboard` показывает общие звонки («Идёт 2-я пара, звонок через 25 мин»), список звонков, избранные места, недавние маршруты и «Где ближайший». Нет ни аудитории, ни дисциплины, ни преподавателя, ни кнопки маршрута к паре, потому что нет данных о расписании групп (`bells.js`: «Личного расписания на сайте нет»).

**Цель.** Одно нажатие от главной до маршрута к аудитории ближайшей пары.

**Зависимость `[BACKEND][ДОПУЩЕНИЕ Д-1]`.** Нужен источник `GET /api/schedule.php?group=ИС-21&date=2026-11-16` → JSON:

```json
{
  "group": "ИС-21",
  "date": "2026-11-16",
  "updatedAt": "2026-11-15T18:00:00+03:00",
  "source": "Учебная часть, выгрузка от 15.11",
  "lessons": [
    { "pair": 1, "start": "09:00", "end": "10:30",
      "subject": "Базы данных", "roomId": "class-217", "roomLabel": "217",
      "teacher": "Иванов И. И.", "note": null, "changed": false }
  ]
}
```
`roomId` — id из `data.js`; если сопоставить нельзя, `roomId: null` и показывается только `roomLabel`. Фронтенд не угадывает соответствие.

**Предлагаемое решение. Два уровня виджета.**

*Уровень 0 (без группы или без данных расписания — работает уже сейчас):* карточка звонков, как сейчас, + кнопка «Указать группу» (если расписание доступно на сервере) + «Мои места».

*Уровень 1 (группа выбрана, расписание есть) — карточка пары:*

```
┌──────────────────────────────────────────┐
│ ● Сейчас идёт · до 10:30 (осталось 24 мин)│  ← статус-чип
│ Базы данных                               │  ← --text-lg 600
│ Каб. 217 · 2 этаж        Иванов И. И.     │  ← аудитория — ссылка
│ 09:00–10:30 · 1-я пара                    │
│ [ ➜ Построить маршрут ]   [ Вся неделя ]   │  ← primary + ghost
├──────────────────────────────────────────┤
│ Далее: 10:40 Математика · каб. 305        │  ← одна строка
└──────────────────────────────────────────┘
```

**Логика статусов (вычисление на клиенте по `lessons` и текущему времени устройства):**

| Условие | Статус-чип | Что в карточке | Таймер |
|---|---|---|---|
| Сейчас между `start` и `end` пары | «Сейчас идёт» (`--c-success`) | Текущая пара | «до конца N мин» |
| До ближайшей пары ≤ 15 мин | «Скоро начнётся» (`--c-warning`) | Следующая пара | «через N мин», при < 1 мин «начинается» |
| Перемена/обед, до следующей > 15 мин, или утро до первой пары | «Следующая пара» (`--c-info`) | Следующая пара | «в 10:40 (через 1 ч 05 мин)» |
| Пар больше нет сегодня | «Занятий сегодня больше нет» | Первая пара следующего учебного дня: «Завтра в 9:00 · Физика · каб. 114» | — |
| Выходной/праздник (`holidays.js`) | «Сегодня занятий нет» | То же «ближайший учебный день» | — |
| В паре `changed: true` | Дополнительный чип «Изменение» (`--c-warning`) | `note` из данных | — |

- Таймер — минутная точность, пересчёт по `setTimeout` до следующей границы минуты (а не `setInterval(30000)`), плюс пересчёт по `visibilitychange` (вкладка вернулась из фона) — иначе на телефоне после разблокировки показывается устаревший статус.
- Смена статуса не перерисовывает всю главную: `MyDay` подписан на свой хук `useLessonNow(lessons)`.
- Обновление данных: при открытии главной, при возврате во вкладку, если `updatedAt` старше 30 мин, и раз в 30 мин, пока вкладка видима. Стратегия stale-while-revalidate: сразу показать кеш (`localStorage`, с датой), обновить в фоне. Если данные изменились, карточка обновляется без анимации-мигания; если изменилась **аудитория текущей/следующей пары** — подсветка строки аудитории `--c-warning-subtle` на 3 с + текст «Аудитория изменена» остаётся до конца пары.

**Действия.**
- Нажатие на «Каб. 217» → `/map?floor=2&room=class-217` (выбор + центрирование, 02).
- «Построить маршрут» → `/route?to=class-217&from=<текущая точка>`. Начало: «Вы здесь» (если есть QR/GPS-точка из `readHere()`), иначе главный вход `entrance-1`, иначе — спросить в поле «Откуда» с фокусом. Этаж и корпус выбираются автоматически маршрутом (02).
- `roomId: null` → кнопка «Построить маршрут» заменяется на «Найти “ауд. 2-17” в поиске» (передать `roomLabel` в поиск).
- «Вся неделя» → раздел «Расписание».

**Выбор группы.** Поле-комбобокс «Ваша группа» (список групп с сервера) + «Я преподаватель» (тогда — расписание по ФИО, `[BACKEND]`). Хранение — `localStorage` (`logos-my-group`, вписать в `privacy-items.js`). Регистрация не требуется.

**Состояния.**

| Состояние | Отображение |
|---|---|
| loading (нет кеша) | Скелетон карточки той же высоты (132 px mobile / 180 px desktop) |
| loading (есть кеш) | Кеш + маленькая надпись «обновляется…» без спиннера |
| success | Как выше |
| empty: группа не выбрана | «Выберите группу, чтобы видеть свои пары и аудитории» + комбобокс |
| empty: нет пар | См. таблицу статусов |
| error, есть кеш | Кеш + «Не удалось обновить. Данные от 15.11, 18:00 · Повторить» |
| error, нет кеша | Карточка звонков (уровень 0) + «Расписание сейчас недоступно · Повторить» |
| offline | Кеш + бейдж «Офлайн, данные от …» |
| группа не найдена на сервере | «Группа ИС-21 не найдена в расписании. Проверьте написание» + выбор |

**Технические требования.**
- Хук `useSchedule(group)` (кеш, SWR, отмена `AbortController` при смене группы, защита от гонок — ответ применяется, только если группа не сменилась).
- Хук `useLessonNow(lessons, now)` — чистая функция `lessonState(lessons, now)` в отдельном модуле с unit-тестами по образцу `bells.test` (границы минут, понедельник с РОВ, праздники, переход через полночь).
- Время: только локальное время устройства (как сейчас в `bells.js`); показать предупреждение, если часовой пояс устройства ≠ `Europe/Moscow` `[уточнить часовой пояс колледжа]`.
- Обратный отсчёт объявляется скринридеру **не** каждую минуту: `aria-live` только на смену статуса.

**Адаптивность.** Mobile: одна карточка пары + строка «Далее»; «Мои места» — ниже на главной, отдельной секцией. Desktop: колонка справа от карты-превью (03), под карточкой — «Мои места» и недавние маршруты.

**Критерии приёмки.**
1. При подставленном времени 09:05 (фейковые часы в тесте) показывается «Сейчас идёт», пара 1, «до конца 85 мин».
2. 10:32 (перемена, следующая в 10:40) → «Скоро начнётся», следующая пара, «через 8 мин».
3. 16:00 последнего дня недели → «Занятий сегодня больше нет» и первая пара следующего учебного дня (с учётом воскресенья и праздников).
4. Нажатие «Построить маршрут» открывает маршрут, этаж назначения переключается автоматически; общее число нажатий от главной — 1.
5. Вкладка в фоне 40 мин → при возврате статус и таймер корректны без перезагрузки.
6. Без сети с кешем видна последняя версия с датой; без кеша — карточка звонков.
7. Без бэкенда расписания (Д-1 не выполнено) виджет работает в уровне 0 без ошибок в консоли.

**Приоритет:** P0 — уровень 0 (уже частично есть, доработать таймер и состояния); P1 — уровень 1 (после Д-1).

### 05. Умный поиск и Autocomplete

**Текущая проблема.** См. A-1 и A-8. Дополнительно: на главной преподаватели всегда выше мест (запрос «2» даёт сначала преподавателей по совпадению?), ограничения разные; `onBlur` закрывает список через `setTimeout(130)` — хрупко; неудачные запросы отправляются на сервер (`reportMiss`) на каждый ввод — нужно убедиться в debounce.

**Цель.** Один движок и один компонент, одинаковые результаты везде; от ввода до открытия места — Enter.

**Предлагаемое решение.**

*Архитектура:*
- `src/search/index.js` — единый движок: `search(query, { limit, scopes })` → `{ groups: [{ type, items: [{ id, type, title, subtitle, floor, building, score, highlights }] }] }`.
- `SearchCombobox` — единственный UI-компонент (шапка, hero, поля «Откуда/Куда» маршрута, поиск на карте). Различаются только пропсы: `scopes`, `onSelect`, `variant`.

*Источники и индекс:*

| Тип | Поля | Источник | Где считается |
|---|---|---|---|
| Помещение | номер, название, `aliases`, категория | `data.js` | Клиент, индекс строится один раз при загрузке модуля |
| Подразделение (учебная часть, бухгалтерия…) | то же | `data.js` категория «Администрация» | Клиент |
| Преподаватель | ФИО, должность, предметы | `teachers.json` (загружается лениво при первом фокусе в поиске) | Клиент |
| Дисциплина, группа `[Д-1]` | название, группа | расписание | Сервер `[BACKEND]` `GET /api/schedule-search.php?q=` |

Объём данных маленький (47 мест, ~100 преподавателей): поиск по местам и преподавателям — полностью на клиенте, синхронно, **без debounce** (< 1 мс). Debounce 250 мс применяется только к серверным источникам (группы/дисциплины) и к `reportMiss` (отправлять «промах» через 1 500 мс неизменного запроса, не чаще раза на уникальный запрос за сессию).

*Алгоритм ранжирования (нормализация → совпадение → вес):*
1. Нормализация: нижний регистр (`toLocaleLowerCase('ru')`), `ё→е`, удаление пунктуации и «№», «каб», «кабинет», «ауд» как стоп-слов; схлопывание пробелов. Раскладка: если запрос целиком в латинице и не даёт результатов, повторить с конвертацией раскладки (`ghtgjl` → «препод»). Транслитерация не нужна.
2. Числовой запрос (`/^\d{1,4}$/`): точное совпадение номера = 1000; номер начинается с запроса = 800 («21» → 210–219); иначе номер не участвует.
3. Текст: для каждого токена запроса — совпадение с началом слова в названии = 100, в aliases = 60, в предметах преподавателя = 40, подстрока внутри слова = 20 (только для токенов ≥ 3 символов). Все токены должны совпасть (AND).
4. Опечатки: для токенов ≥ 5 символов — расстояние Дамерау–Левенштейна ≤ 1 к началу слова = 30. Только если точных совпадений < 3.
5. Бонусы: место в «Недавних» +50; место на этаже «Вы здесь» +10.
6. Тай-брейк: тип (место > преподаватель > дисциплина), затем номер по возрастанию.

*Группировка и лимиты в выпадающем списке:* «Места» (до 6), «Преподаватели» (до 3), «Занятия» (до 3, `[Д-1]`). Порядок групп — по максимальному счёту в группе (при запросе «217» места сверху; при «Иванов» — преподаватели). Итого не более 12 строк.

*Подсветка:* совпавшие диапазоны в `title`/`subtitle` оборачиваются в `<mark>` (фон `--c-highlight`, без смены цвета текста). Для опечаток не подсвечивать.

*Пустой запрос (фокус в пустом поле):* «Недавние» (до 5, с кнопкой «Очистить») → «Часто ищут» (`quickPlaces`) → строка «Рядом: туалет · выход · столовая · медпункт · лифт» (как сейчас в `SearchDialog`).

**Алгоритм взаимодействия.**
1. Пользователь фокусирует поле → открывается список пустого запроса.
2. Ввод → синхронный поиск по клиентскому индексу, список обновляется в том же кадре; серверная группа — после debounce 250 мс, со скелетоном одной строки в своей группе.
3. Стрелки ↑/↓ перемещают активную строку (с циклом в конце списка: нет; упор). `Home`/`End` — первая/последняя. Активная строка прокручивается в зону видимости.
4. `Enter` — открыть активную строку (по умолчанию активна первая). `Alt+Enter` — сразу маршрут (сохранить текущее поведение). `Esc` — закрыть список; второй `Esc` — очистить поле; в диалоге — закрыть диалог.
5. Выбор места: `rememberPlace(id)` → переход `/map?floor=&room=` → карта переключает этаж, центрируется, подсвечивает (02, анимация 08) → открывается карточка места с главной кнопкой **«Маршрут сюда»** и вторичной «Избранное».
6. Выбор преподавателя: карточка преподавателя в списке раскрывается на месте (ФИО, должность, предметы, «Обычно: кабинет 305» — **только если кабинет есть в данных**, с пометкой «по данным справочника») + «Показать кабинет». Если кабинета нет — «Кабинет не указан. Спросите в учебной части» + «Как пройти в учебную часть». Сейчас при отсутствии кабинета поиск молча ведёт в учебную часть — это подмена результата, её убрать.
7. Выбор дисциплины/группы `[Д-1]`: переход в «Расписание» с фильтром.
8. Нет результатов: «По запросу “21Б” ничего не нашлось» + подсказки: «Проверьте номер: кабинеты на 1 этаже — 101–160, на 2 этаже — 201–2xx» `[уточнить диапазоны по data.js]`, «Открыть список всех мест», «Спросить помощника» (передаёт запрос в ИИ).

**Состояния.** closed, open-empty-query, open-results, open-loading (только серверная группа), open-no-results, open-error (серверная группа: «Занятия сейчас недоступны», места продолжают работать), disabled (не применяется).

**Технические требования и a11y (ARIA 1.2 combobox, паттерн APG «Combobox with listbox popup»):**
- `<input role="combobox" aria-expanded aria-controls aria-activedescendant aria-autocomplete="list">`; список `<ul role="listbox">` с `<li role="option" id aria-selected>`; группы — `<ul role="group" aria-labelledby>` внутри listbox.
- **Внутри `role="option"` нет ссылок и кнопок.** Действие «Маршрут» доступно через `Alt+Enter` и через карточку места после выбора; в мышином интерфейсе — отдельная кнопка справа, **вынесенная за пределы option** (строка = `div` с option и соседней кнопкой; кнопка `tabindex="-1"`, т. к. доступна с клавиатуры через сочетание; подсказка сочетания в футере списка).
- Количество результатов объявляется отдельным `<div role="status" class="visually-hidden">` с задержкой 500 мс после окончания ввода: «8 результатов». `aria-live` со списка убрать.
- Закрытие по клику вне — через `pointerdown` на документе с проверкой `contains`, а не `onBlur + setTimeout`.
- Позиционирование списка: в шапке/hero — абсолютное под полем внутри обёртки (`position: relative`), без портала, если нет обрезки `overflow`; на mobile — полноэкранный слой поиска (07).
- `inputmode="search"`, `enterkeyhint="search"`, `autocapitalize="off"`, `spellcheck="false"`, шрифт ≥ 16 px.
- Голосовой ввод (`VoiceSearchButton`) сохраняется в поле, только если `SpeechRecognition` поддерживается; иначе кнопка не рендерится (не `disabled`).
- Unit-тесты движка: таблица из ≥ 30 запросов → ожидаемый первый результат (номера, части номеров, опечатки, раскладка, «ё», ФИО в разных формах «Иванов», «иванов и и», «Иван Ив»).

**Адаптивность.** Desktop: выпадающий список под полем, ширина = ширина поля, max-height 60vh. Mobile: тап по полю в шапке открывает полноэкранный слой: поле сверху (фокус, клавиатура открыта), результаты под ним, кнопка «Отмена» справа от поля; результаты не перекрываются клавиатурой (`visualViewport` resize → `max-height`).

**Критерии приёмки.**
1. Один и тот же запрос в шапке, на главной и в поле «Куда» маршрута возвращает одинаковые первые 6 мест в одинаковом порядке.
2. «217», «каб. 217», «№217» → первый результат кабинет 217. «21» → кабинеты 210–219 первыми. «столовка»/«сталовая» → Столовая. «ghtgjl» → результаты как по «препод».
3. Время от нажатия клавиши до отрисовки результатов по местам ≤ 16 мс (Performance-профиль), INP поля ≤ 100 мс.
4. axe: 0 нарушений на открытом списке; VoiceOver объявляет «Кабинет 217, 2 этаж, 1 из 8».
5. Нет вложенных интерактивных элементов внутри `role="option"` (проверка скриптом).
6. Запрос без результатов отправляет `search-miss` не более 1 раза за 1 500 мс неизменного ввода.
7. Выбор места → карта на нужном этаже, место подсвечено, кнопка «Маршрут сюда» в фокусе (клавиатурный сценарий) — без дополнительных нажатий.

**Приоритет:** P0.

### 06. ИИ-помощник

**Текущая проблема.** См. A-7. Помощник — общий чат (DeepSeek, Markdown, квизы, графики, формулы, фото). Местоположения модель берёт из `ai-knowledge.txt`; кнопки появляются, только если модель вставила корректную ссылку `/route?...`. Расписания групп у модели нет. В системном промпте уже есть правило не выдумывать факты (строка 461 `ai-chat.php`) — это правильно, но опирается на послушание модели.

**Цель.** Навигационные ответы — детерминированные (из данных), модель только понимает запрос и формулирует. Любой факт о месте/времени/человеке имеет источник.

**Архитектура `[BACKEND]`: «понимание → инструменты → ответ».**

1. Сервер передаёт модели описание **инструментов** (function calling, если API DeepSeek его поддерживает для выбранной модели — `[уточнить по документации провайдера]`; иначе — строгий JSON-формат «намерения» в ответе модели с серверной валидацией):
   - `find_place(query)` → результаты единого поискового движка (05; на сервере — та же логика, данные `data.js` экспортируются при сборке в `public/api/places.json`, как сейчас для звонков).
   - `group_now(group, datetime)` `[Д-1]` → пара группы из расписания.
   - `teacher_schedule(name, datetime)` `[Д-1]` → пары преподавателя.
   - `route(from, to, prefs)` → только проверяет существование точек; сам маршрут строит клиент.
2. Ответ сервера клиенту — не только Markdown, а JSON:

```json
{
  "text": "Сейчас у ИС-21 «Базы данных» в кабинете 217 (2 этаж), до 10:30.",
  "facts": [{ "kind": "lesson", "source": "schedule", "updatedAt": "2026-11-15T18:00:00+03:00" }],
  "actions": [
    { "type": "open_place", "roomId": "class-217", "label": "Показать на карте" },
    { "type": "route", "to": "class-217", "from": null, "label": "Построить маршрут" }
  ],
  "sig": "…"
}
```
3. Клиент рендерит `text` (как сейчас — безопасно, без HTML), под ним **карточку результата** из `actions`/`facts`: мини-превью этажа с подсвеченным местом (тот же `FloorMap` в режиме `preview`), строка «2 этаж · Кабинет 217», кнопки действий. Ссылки внутри текста продолжают работать как сейчас (обратная совместимость).
4. Клиент проверяет каждое `roomId` по `data.js`; неизвестный id → действие не показывается, в лог `client-error`.

**Сценарии.**

*A. «Где сейчас проходит пара у группы ИС-21?»*
- Сервер: распознаёт группу (нормализация «ис21», «ИС 21»), вызывает `group_now`.
- Есть данные → «Сейчас у ИС-21 “Базы данных”, кабинет 217, 2 этаж, до 10:30. Преподаватель — Иванов И. И.» + карточка + [Показать на карте] [Построить маршрут] + подпись мелким шрифтом «По расписанию учебной части от 15.11, 18:00».
- Перемена → «Сейчас перемена. Следующая пара у ИС-21 в 10:40 — Математика, кабинет 305».
- Нет такой группы → «Не нашёл группу “ИС-21” в расписании. Есть ИС-21-1 и ИС-21-2 — какую?» + чипы-кнопки групп.
- Расписания нет на сервере (Д-1 не выполнено) → «У меня нет расписания групп. Его можно уточнить в учебной части — показать, как туда пройти?» + [Маршрут в учебную часть]. Модель **не** называет аудиторию.

*B. «Как пройти в деканат?»*
- «Деканат» отсутствует в `data.js` как название → поиск по `aliases`. `[Уточнить: есть ли в колледже деканат; ближайшее по смыслу — «Учебная часть»]`. Если совпадение только по смыслу, ответ явно это говорит: «Отдельного деканата на плане нет. Вопросы учёбы решает учебная часть — 1 этаж, кабинеты 141–160».
- Карточка + [Построить маршрут] + кнопка «Шаги текстом»: раскрывает список шагов из `route-steps.js` прямо в чате («1. От главного входа идите прямо по коридору 40 м…»). Маршрут строит клиент; точка старта — «Вы здесь» или главный вход (с пометкой «от главного входа · изменить»).

*C. «Где находится преподаватель Иванов?»*
- Сервер ищет преподавателя (`find_place` с типом teacher). Неоднозначность (2 Иванова) → уточнение чипами с ФИО и должностями.
- Есть расписание `[Д-1]` и пара идёт сейчас → «По расписанию у Иванова И. И. сейчас пара в кабинете 217 (до 10:30). Это расписание, а не фактическое местоположение». + карточка.
- Нет пары сейчас / нет расписания → «Я не знаю, где сейчас находится Иванов И. И. — данных о местоположении людей у меня нет. По справочнику он ведёт “Базы данных”; уточнить можно в учебной части». Никаких предположений вида «скорее всего в учительской».
- Запрещено: отвечать о перемещениях, «был/ушёл», домашних данных, телефонах, которых нет в открытом справочнике.

*D. «Как быстрее добраться из библиотеки до кабинета 305?»*
- Сервер распознаёт две точки → `actions: [{ type: "route", from: "library", to: "class-305", prefs: { avoid: null } }]`.
- Клиент строит маршрут (`calculateIndoorRoute`), учитывает закрытые лестницы/лифт из `notices`, показывает карточку: «≈ 2 мин, 160 м, по центральной лестнице» + мини-карта с линией + [Открыть маршрут].
- «Без лестниц» / «на коляске» в запросе → `prefs.avoid: "stairs"`; если лифт закрыт — честно: «Лифт сейчас не работает, маршрут без лестниц недоступен».
- Цифры времени и длины берёт клиент из маршрутизатора; модель их не придумывает (в `text` вставляются плейсхолдеры, которые клиент заполняет, или текст формирует клиент из шаблона).

*E (дополнительный). «Мне на пару, куда идти?»* — при выбранной группе (04) клиент добавляет в запрос контекст `{ group }`; ответ = данные «Мой день» + маршрут.

**Структура интерфейса чата.**
- Desktop: `/ai` — колонка 720 px по центру: лента сообщений, поле ввода внизу (sticky), над полем — чипы быстрых запросов (только при пустом чате и после ответа — 3 контекстных). Слева 260 px — список чатов (как сейчас), сворачиваемый.
- Mobile: `/ai` во вкладке нижней навигации «Помощник», поле ввода над нижней навигацией с учётом клавиатуры (`visualViewport`), safe area.
- Точка входа из поиска: «Спросить помощника» при пустых результатах (05) — передаёт запрос.
- Быстрые запросы (стартовые): «Где моя следующая пара?» (если группа выбрана), «Как пройти в учебную часть?», «Где ближайший туалет?», «Где поесть?», «Маршрут без лестниц до …».
- Нестандартные функции (квизы, графики, фото расписания, формулы) остаются, но не в стартовых чипах: они не навигационные.

**Состояния ожидания.**
- 0–300 мс: ничего (нет мигания).
- > 300 мс: пузырь ассистента со скелетоном из 2 строк и подписью «Ищу на плане…» / «Смотрю расписание…» (по типу вызванного инструмента, если сервер стримит этапы; если нет — общее «Думаю…»).
- Кнопка «Остановить» вместо «Отправить» во время ожидания (`AbortController`, уже есть `signal` в `askAgent`).
- Таймаут 30 с → ошибка.

**Обработка ошибок.**

| Ошибка | Сообщение | Действие |
|---|---|---|
| Сеть недоступна | «Нет соединения. Вопрос сохранён» | «Отправить снова»; поиск мест работает офлайн — кнопка «Найти на карте без помощника» |
| 429 / лимит | «Помощник сейчас перегружен. Попробуйте через минуту» | Таймер на кнопке повтора |
| 5xx / таймаут | «Помощник не ответил» | «Повторить» |
| Ответ не прошёл валидацию (неизвестный roomId) | Действие скрыто; текст показан с пометкой «Не удалось проверить место на плане» | — |
| Модерация (`ai-guard.php`) | Нейтральное «На такой вопрос ответить не могу» | — |

**Контекст диалога.** Последние 20 сообщений (как сейчас `MAX_HISTORY`), плюс структурированный контекст: `{ group, here: roomId | null, lastPlace: roomId | null, prefs }`. «А как туда пройти?» после ответа о кабинете 217 использует `lastPlace`. Контекст виден пользователю: под полем ввода чип «Группа ИС-21 · ×» и «От: главный вход · изменить».

**Ограничения ИИ (показать текстом в пустом чате, одной строкой + «Подробнее»):** «Помощник отвечает по плану колледжа и расписанию учебной части. Он не знает, где находятся люди, и может ошибаться — проверяйте важное в учебной части».

**Передача результата в карту.** Действия `open_place` и `route` — обычные переходы роутера (`/map?room=`, `/route?from=&to=&mode=`), поэтому история «Назад» возвращает в чат с сохранённой позицией прокрутки. На desktop ≥ 1280 — опционально (P2) открытие карты в боковой панели рядом с чатом без ухода со страницы.

**Технические требования.**
- Схема ответа валидируется на клиенте (ручной валидатор, без новых зависимостей); неизвестные `type` игнорируются.
- Подпись `sig` сохраняется (уже используется против подделки истории).
- Логирование: тип запроса (навигация/расписание/прочее), был ли вызов инструмента, был ли отказ — без текста запроса, если нет согласия на функциональные cookie (`consent.js`).
- Набор регрессионных «золотых» запросов (≥ 20) с ожидаемыми `actions` прогоняется скриптом против staging-сервера перед релизом промпта.

**Критерии приёмки.**
1. Сценарии A–D дают ответы с карточкой и кнопками; кнопки ведут на правильный этаж и место.
2. При выключенном источнике расписания сценарии A и C **не содержат номеров аудиторий** (проверка по 20 прогонам «золотого» набора: 0 упоминаний номеров).
3. Каждый ответ о паре содержит дату актуальности данных.
4. Длина маршрута и время в ответе D совпадают с `/route` для тех же точек.
5. «Остановить» прерывает запрос, поле снова активно, частичный ответ не сохраняется как ответ.
6. Сценарии проходятся с клавиатуры и скринридером; новое сообщение ассистента объявляется один раз (`role="log"` на ленте).

**Приоритет:** P1 (структурированные действия и честные отказы), P2 (инструменты расписания после Д-1), P3 (карта в боковой панели).

### 07. Мобильная адаптация

**Текущая проблема.** См. A-4; карта встроена в документную прокрутку, жесты карты и страницы конфликтуют (в коде — обходы для Safari); 49 разных брейкпоинтов.

**Цель.** Все основные действия — одной рукой; карта — полноэкранный инструмент.

**Bottom Navigation (< 768 px), 4 вкладки:**

| Вкладка | Иконка (lucide) | Маршрут | Назначение |
|---|---|---|---|
| Главная | `House` | `/` | Поиск, «Мой день», избранное |
| Карта | `Map` | `/map` | Полноэкранная карта, поиск по карте, карточка места |
| Расписание | `CalendarClock` | `/schedule` (`[Д-1]`; до этого `/notifications` с подписью «Звонки») | Пары, звонки, напоминания |
| Помощник | `MessageCircle` | `/ai` | ИИ |

Почему не 5 и почему нет «Маршрута»: маршрут — это **действие над местом** (кнопка в карточке места, в «Мой день», в поиске), а не самостоятельное место назначения; отдельная вкладка дублирует эти входы. Всё остальное — меню «Ещё» в шапке (иконка `Menu` справа) в виде нижней шторки.

- Высота 64 px + `env(safe-area-inset-bottom)`; иконка 24 px + подпись 12 px (подписи обязательны). Активная вкладка: иконка с заливкой + цвет `--c-primary` + `aria-current="page"`.
- Повторное нажатие на активную вкладку: прокрутка к началу (Главная/Расписание/Помощник) или «вписать этаж» (Карта).
- Нижняя навигация скрывается только когда открыта клавиатура (поле в фокусе) и в режиме ведения по маршруту (`WalkMode`).

**Поиск на mobile.** Поле-кнопка в шапке → полноэкранный слой поиска (05). На вкладке «Карта» поле поиска плавает поверх карты сверху (отступ `--space-3`, высота 48).

**«Мой день» на mobile.** Компактная карточка 132 px сразу под hero (03), кнопка «Маршрут» — справа внизу карточки, в зоне большого пальца.

**Полноэкранная карта (вкладка «Карта»).**
- Структура: карта на весь экран под шапкой 56 px и над нижней навигацией; поверх — поле поиска (сверху), переключатель этажей (справа, по центру по вертикали, в зоне большого пальца для правшей; в настройках «Ещё» — «Элементы карты слева» для левшей, P3), кнопки зума/«моё место»/легенда (справа над шторкой).
- Нижняя шторка (bottom sheet) с тремя позициями: свёрнута (заголовок 72 px: «Кабинет 217 · 2 этаж» + кнопка «Маршрут»), половина (≈ 50 % высоты: карточка места, фото, описание), развёрнута (90 %: список мест этажа — альтернативное представление, 09). Перетаскивание за «ручку» 32×4 (область захвата 44 px по высоте), снап к позициям, кнопка-«ручка» доступна с клавиатуры/скринридера (`button aria-expanded` переключает позиции).
- Без выбранного места шторка в свёрнутом виде показывает «Этаж 1 · 23 места» → разворачивается в список.

**Жесты и конфликт с прокруткой.**
- На вкладке «Карта» документ не прокручивается (`overflow: hidden` на `html` только этого маршрута; `overscroll-behavior: none`), у карты `touch-action: none`: один палец — pan, два — pinch, двойной тап — zoom.
- Встроенная карта-превью на главной: `touch-action: pan-y` и **без** pan/zoom — тап открывает вкладку «Карта» с тем же видом. Это полностью убирает конфликт «хотел прокрутить страницу — сдвинул карту».
- Шторка: вертикальный жест внутри шторки двигает шторку, пока она не развёрнута; в развёрнутом виде — прокручивает список; `overscroll-behavior: contain`.
- Pinch-to-zoom страницы браузером **не запрещать** (`user-scalable=no` не использовать; сейчас в `index.html` его нет — сохранить).

**Области нажатия.** Все интерактивные элементы ≥ 44×44 CSS px на `pointer: coarse` (визуальный размер может быть меньше, область — через padding или `::before` с `inset: -N`). Расстояние между соседними целями ≥ 8 px. Помещения на карте при свёрнутом масштабе могут быть меньше 44 px — для них работает «выбор ближайшего»: тап выбирает помещение, чей контур ближе всего к точке в радиусе 22 px.

**Safe Area.** `viewport-fit=cover` уже стоит. Применять `env(safe-area-inset-*)`: шапка (top), нижняя навигация и шторка (bottom), плавающие кнопки карты (left/right в альбомной ориентации).

**Брейкпоинты (заменяют 49 текущих значений).**

| Токен | Диапазон | Устройство | Ключевые отличия |
|---|---|---|---|
| `sm` | < 768 | Смартфон | Bottom nav, шапка 56, шторка на карте, одна колонка |
| `md` | 768–1023 | Планшет | Bottom nav сохраняется в портретной; в альбомной (≥ 1024 по ширине) — desktop-раскладка; карта: панель 320 справа (альбомная) или шторка (портретная) |
| `lg` | 1024–1279 | Небольшой ноутбук | Шапка с навигацией, без bottom nav; карта + панель 360 |
| `xl` | ≥ 1280 | Desktop | Контейнер 1200 px, подписи у «Ещё», полная ширина поиска |

Медиазапросы — только `min-width` (mobile-first). Для специфики ввода — `(pointer: coarse)` и `(hover: hover)`, а не ширина.

**Технические требования.**
- `BottomNav` рендерится в `App` вне `<main>` (`<nav aria-label="Основные разделы">`), читает конфиг из `src/navigation.js`.
- `<main>` получает `padding-bottom: calc(64px + env(safe-area-inset-bottom))` на `sm/md`.
- Шторка: CSS `transform: translateY()` + Pointer Events, позиции в `dvh`; `will-change: transform` только во время перетаскивания.
- `100vh` заменить на `100dvh` (с `@supports` фолбэком на `100vh`).

**Критерии приёмки.**
1. На 375×667 и 390×844: нижняя навигация с 4 вкладками, все вкладки 44+ px по высоте; нет горизонтальной прокрутки ни на одной странице.
2. На главной вертикальный свайп по карте-превью прокручивает страницу; на вкладке «Карта» любой жест управляет картой, страница не сдвигается (проверка на iOS Safari 17+ и Chrome Android).
3. Шторка: 3 позиции, переключение кнопкой-ручкой доступно VoiceOver/TalkBack.
4. На iPhone с вырезом в альбомной ориентации ни один элемент управления не попадает под вырез/индикатор «Домой».
5. При открытой клавиатуре в поиске поле и первые 3 результата видны; нижняя навигация скрыта.
6. Аудит скриптом: на `pointer: coarse` 0 интерактивных элементов меньше 44×44 (кроме помещений карты, для которых работает «ближайший»).

**Приоритет:** P0 (bottom nav, полноэкранная карта, конфликт жестов, цели 44 px, safe area), P1 (шторка с 3 позициями), P3 (режим для левшей).

### 08. Микроанимации и интерактивные состояния

**Текущая проблема.** 32 блока `prefers-reduced-motion` в разных файлах, `motion.css`, `Reveal` с задержками на главной (карточки «Часто ищут» появляются с `delay: index * 60`), View Transition при смене темы, `page-enter` с `translateY(7px)`. Нет единых токенов длительностей; часть анимаций — декоративные (появление карточек при прокрутке).

**Цель.** Анимация только там, где она объясняет изменение состояния (что откуда пришло, что выбрано, куда идти).

**Токены движения:**

| Токен | Значение | Применение |
|---|---|---|
| `--dur-instant` | 0 ms | reduced-motion |
| `--dur-fast` | 120 ms | hover, active, фокус, появление подсказок |
| `--dur-base` | 200 ms | открытие поповеров, смена этажа, шторка (снап) |
| `--dur-slow` | 320 ms | перелёт камеры карты к месту |
| `--dur-route` | 600–1200 ms | прорисовка маршрута (по длине) |
| `--ease-out` | `cubic-bezier(.2, 0, 0, 1)` | появление, перемещение к цели |
| `--ease-in-out` | `cubic-bezier(.4, 0, .2, 1)` | смена этажа, камера |
| `--ease-in` | `cubic-bezier(.4, 0, 1, 1)` | исчезновение |

**Спецификация анимаций.**

**Удалить:** `Reveal` (появление при прокрутке) на главной и в списках; `page-enter` (сдвиг при смене страницы — без пользы и даёт мерцание); View Transition-круг темы оставить только на desktop (как сейчас) — это единственный «декоративный» эффект, допустим, т. к. запускается явным действием и не блокирует.

**Технические требования.**
- Анимировать только `transform`, `opacity`, `stroke-dashoffset`; `background-color`/`border-color` — только на мелких элементах (кнопки, чипы). Не анимировать `width`, `height`, `top`, `left`, `box-shadow`, `filter`.
- Ни одна анимация не блокирует ввод: клики во время анимации обрабатываются; `pointer-events` не отключаются.
- Единый файл `motion.css` с токенами + `@media (prefers-reduced-motion: reduce) { :root { --dur-fast: 0ms; … } }`; JS-анимации читают `matchMedia('(prefers-reduced-motion: reduce)')` через один хук `useReducedMotion()`. Удалить 32 разрозненных блока.
- `will-change` — только на время анимации (ставится и снимается в JS), не в статичном CSS.

**Критерии приёмки.**
1. В Performance-профиле прорисовки маршрута и смены этажа нет Layout/Recalculate Style на кадр (только Composite/Paint), ≥ 55 FPS на CPU ×4.
2. При `prefers-reduced-motion: reduce` (эмуляция в DevTools) ни одно перемещение/масштаб не анимируется; приложение полностью работоспособно.
3. Быстрое двойное переключение этажей (2 клика за 100 мс) завершается на правильном этаже без «застрявших» слоёв.
4. В кодовой базе нет значений `transition`/`animation` с литералами длительностей вне токенов (проверка grep/stylelint).

**Приоритет:** P1 (маршрут, этажи, выбор, reduced motion), P3 (пульс, шиммер).

## Раздел 5. Design System

Значения ниже — стартовые; каждое сочетание текст/фон проверяется скриптом контраста при внедрении (критерий 09.2). Значения со звёздочкой (*) требуют подтверждения расчётом.

### 5.1. Цветовые токены (семантические)

Слой примитивов (`--blue-50…900`, `--slate-50…900`, `--green-*`, `--amber-*`, `--red-*`) используется **только** внутри файлов тем. Компоненты используют только семантические токены:

### 5.2. Типографика

Шрифт: Onest Variable (`@fontsource-variable/onest`, уже в зависимостях), фолбэк — системный стек. Моноширинный — для `kbd` и номеров в таблицах (`font-variant-numeric: tabular-nums` вместо моно для чисел).

| Токен | Размер / межстрочный | Начертание | Применение |
|---|---|---|---|
| `--text-xs` | 0.75rem / 1rem (12/16) | 500 | Подписи вкладок нижней навигации, бейджи |
| `--text-sm` | 0.875rem / 1.25rem (14/20) | 400/500 | Вторичный текст, навигация, метаданные |
| `--text-md` | 1rem / 1.5rem (16/24) | 400 | Основной текст, поля ввода |
| `--text-lg` | 1.125rem / 1.625rem (18/26) | 600 | Заголовки карточек, название пары |
| `--text-xl` | 1.5rem / 1.875rem (24/30) | 700 | H1 mobile, H2 desktop |
| `--text-2xl` | 2rem / 2.5rem (32/40) | 700 | H1 desktop |

Ограничения: 6 размеров, 3 начертания (400, 500/600, 700). Длина строки текста ≤ 72 символа (`max-width: 68ch`). Режим «Крупный текст» = `html { font-size: 112.5% }` — всё в `rem` масштабируется.

### 5.3. Отступы и размеры

Шкала 4 px: `--space-1` 4, `--space-2` 8, `--space-3` 12, `--space-4` 16, `--space-5` 20, `--space-6` 24, `--space-8` 32, `--space-10` 40, `--space-12` 48, `--space-16` 64.

- Боковые поля контейнера: 16 (sm), 24 (md), 32 (lg+); контейнер max 1200 px (сейчас `calc(100% - 88px)` даёт 44 px полей на телефоне — слишком много для 360 px).
- Между секциями главной: 32 (sm) / 48 (lg). Внутри карточки: 16 (sm) / 20 (lg).
- Высоты контролов: `--control-sm` 32 (только `pointer: fine`), `--control-md` 40, `--control-lg` 48, `--control-xl` 56 (поле поиска в hero). Минимальная область нажатия `--target-min` 44 на `pointer: coarse`, 24 на `pointer: fine`.
- Иконки: 16 (в тексте `sm`), 20 (в кнопках `md`), 24 (нижняя навигация, кнопки карты).

### 5.4. Радиусы

`--radius-sm` 6 (чипы внутри карточек, `kbd`), `--radius-md` 10 (кнопки, поля), `--radius-lg` 16 (карточки, поповеры, hero-поиск), `--radius-xl` 24 (верх шторки), `--radius-full` 999 (чипы, вкладки-таблетки, маркеры).

### 5.5. Тени (возвышение)

Возвышение сначала границей, тень — только для плавающих слоёв.

| Токен | Значение (светлая) | Применение |
|---|---|---|
| `--shadow-0` | none + граница `--c-border` | Карточки в потоке |
| `--shadow-1` | `0 1px 2px rgb(19 33 58 / .06), 0 1px 3px rgb(19 33 58 / .08)` | Sticky-шапка при прокрутке, hero-поиск |
| `--shadow-2` | `0 4px 12px rgb(19 33 58 / .10)` | Поповеры, подсказки поиска, плавающие кнопки карты |
| `--shadow-3` | `0 12px 32px rgb(19 33 58 / .16)` | Шторка, диалог |

В тёмной теме тени заменяются на `--c-surface` светлее на один шаг + граница 1 px `rgb(255 255 255 / .06)`.

### 5.6. Состояния компонентов

| Состояние | Правило |
|---|---|
| default | Токены компонента |
| hover | Только `@media (hover: hover)`; смена фона на `--c-surface-hover` (нейтральные) или затемнение primary на 1 шаг |
| active / pressed | `--c-surface-pressed`; primary-кнопка `scale(.98)` |
| focus-visible | `outline: 2px solid var(--c-focus); outline-offset: 2px;` + `box-shadow: 0 0 0 4px var(--c-surface)`; никогда `outline: none` без замены |
| selected / current | `--c-primary-subtle` фон + `--c-primary-strong` текст + `aria-current`/`aria-pressed`/`aria-selected` |
| disabled | opacity не используется; текст `--c-text-subtle`, фон `--c-surface-sunken`, `cursor: not-allowed`, нативный `disabled`. Если действие недоступно по бизнес-причине — не disabled, а активная кнопка с объяснением по нажатию |
| loading | `aria-busy="true"`, подпись кнопки сохраняется, спиннер 16 px заменяет иконку; ширина кнопки не меняется |
| error | Граница `--c-danger`, сообщение под полем с иконкой, `aria-invalid` + `aria-describedby` |

### 5.7. Иконки

- Только `lucide-react` (уже в проекте), stroke 2 (1.75 для 24 px), размеры 16/20/24.
- Иконка без подписи — только в `IconButton` с обязательным `aria-label` и всплывающей подсказкой (`title` недостаточно — компонент `Tooltip` по hover и focus, показывается через 400 мс).
- Декоративные иконки рядом с текстом — `aria-hidden="true"`.
- Одна иконка = одно значение во всём продукте (например, `Navigation` — только «маршрут»; сейчас `MapPin` и `Map` используются для карты в разных местах — выбрать `Map`).
- Иконки карты (лестница, лифт, туалет, выход, медпункт, столовая) — отдельный набор SVG-`<symbol>`, согласованный с легендой.

### 5.8. Базовые UI-компоненты

`Button` (primary / secondary / ghost / danger; sizes md, lg; icon-left), `IconButton` (обязателен label), `Chip` (filter / action / status), `SegmentedControl` (этажи, тема, язык — на нативных `button[aria-pressed]` или `radio`), `TextField` (видимый label всегда; placeholder — только пример формата), `Combobox` (примитив для 05), `Card`, `Sheet` (3 позиции), `Popover`, `Dialog` (нативный), `Toast`, `Banner`, `Badge`, `Kbd`, `Skeleton`, `EmptyState`, `ErrorState`, `StaleBadge`, `Tooltip`, `VisuallyHidden`, `SkipLink`.

Тексты кнопок — глагол + объект: «Построить маршрут», «Показать на карте», «Повторить», «Выбрать группу». Запрещены «ОК», «Далее» без объекта, «Отправить» без контекста.
